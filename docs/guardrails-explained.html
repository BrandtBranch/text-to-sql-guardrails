How the guardrails work

An AI turns a plain-English question into a database command. These layers sit between that command and the database, so that a tricked or careless AI cannot leak private data, change anything, or overload the system. Everything below was produced by running the real code on the real (made-up) database.

New to this? Key words
SQL / query
The language used to ask a database for data. A "query" is one command, like SELECT name FROM clients.
Red team
People (or here, me) whose job is to attack a system on purpose, to find weak points before a real attacker does.
Guardrail
A safety layer that checks or limits what a command can do.
Private data
In this made-up database: staff salaries and emails, and a hidden table of fake passwords.
Injection
Hostile instructions hidden in data (like a client note) hoping the AI will obey them.

    2. Which layer stops what?
    
  
    In the order they run, the parser goes first and cheaply refuses most things, so it can look like the only layer that matters. This asks the harder question: switch every other layer off and see how many of the real attacks each one stops on its own. There are  attacks in the suite, and  of them actually work against an unprotected database.
    
  
    
    
    
    
    How to read it: the parser alone stops most attacks, but not the ones that are legal-looking and expensive. The three layers the database itself enforces stop all  between them in this suite, even with no parser at all. That is the suite I wrote, so it shows what I thought of, not everything an attacker might. The parser earns its place by giving clear error messages and refusing early. The other layers are what remains when the parser is wrong. No single layer is the whole answer.
    
  
    

  
    3. The salary puzzle
    
  
    Salary is allowed, but only as an average over five or more people, so nobody's pay is exposed. That sounds safe. It isn't, if you can ask two questions and compare. Switch the fifth layer, the audit, on and off.
    
  
    
    
    
    
    
    
  
    

  
    4. Why not just tell the AI to behave?
    
  
    I sent 23 hostile requests through two Claude models, a larger one and a smaller one, under four setups. The bars show how many caused real harm: private data released, data changed, or the system overloaded.
    
  
    
    
    
    
    The catch: for both models, the safety instruction refused every privacy attack, but it still ran the overload attack, because nobody had thought to mention cost in the instruction. The database's own time limit stopped it. Instructions cover what you anticipated. Limits enforced by the database cover the rest. The smaller model was not easier to attack here. Its weakness was quieter: it sometimes passed hidden instructions on to the reader as if they were ordinary notes.
